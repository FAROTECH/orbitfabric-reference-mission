# 10, Data Products and Storage

Status: tutorial draft  
Scope: tenth step of the progressive Reference Mission tutorial

## Purpose

This step introduces data products and storage intent.

After defining the payload lifecycle, the next question is:

```text
What does the mission produce, preserve and prepare for later downlink?
```

A data product is not just a file. In OrbitFabric, it is a contract-level object that connects producer, type, estimated size, priority, storage policy and downlink intent.

In the Reference Mission, data products are defined in:

```text
mission/data_products.yaml
```

## Operational reason

Telemetry explains observed values. Events explain milestones. Payload lifecycle explains science activity.

Data products explain the durable outputs of that activity.

This matters because a mission does not only perform actions. It must also preserve the evidence and science outputs that those actions produce.

A data product therefore answers:

```text
What was produced?
Who produced it?
How large is it expected to be?
How important is it?
How should it be stored?
How should it be considered for downlink?
```

## Current data products

The current Reference Mission defines three data products:

| Data product | Producer | Type | Priority | Tutorial role |
|---|---|---|---|---|
| `critical_housekeeping` | `obc` | `diagnostic_dump` | `critical` | Essential engineering health product. |
| `radiation_histogram` | `radiation_event_payload` | `histogram` | `high` | Main science product generated by the payload. |
| `scenario_evidence_log` | `obc` | `diagnostic_dump` | `medium` | Engineering evidence product for scenario review. |

This set is intentionally compact.

It covers the three output classes needed by the tutorial:

- critical engineering evidence;
- science output;
- scenario review evidence.

## What each data product declares

Each data product can declare several contract-level properties:

| Property | Role |
|---|---|
| `id` | Stable machine-readable data-product identifier. |
| `producer` | Subsystem or payload that produces it. |
| `producer_type` | Whether the producer is a subsystem or payload. |
| `type` | Product category. |
| `estimated_size_bytes` | Approximate expected size. |
| `priority` | Operational priority. |
| `payload` | Payload association, when applicable. |
| `storage` | Storage intent and retention policy. |
| `downlink` | Downlink handling policy. |
| `description` | Human-readable operational meaning. |

The important point is that a data product carries operational intent, not just a filename.

## Storage intent

Each data product declares storage intent.

The current model uses storage classes such as:

| Storage class | Tutorial meaning |
|---|---|
| `housekeeping` | Engineering health data. |
| `science` | Payload science output. |
| `engineering` | Scenario or operational evidence. |

Each product also declares retention and overflow policy.

For example, the science histogram has:

```text
storage class: science
retention: 30d
overflow_policy: drop_oldest
```

This does not define a filesystem.

It defines how the mission contract expects the product to be treated at a policy level.

## Downlink intent

Each data product also declares a downlink policy.

The current model uses:

| Downlink policy | Tutorial meaning |
|---|---|
| `priority_based` | Product should be considered according to operational priority. |
| `deferred` | Product can be downlinked later as engineering evidence. |

This step does not yet define contact windows or downlink flows.

It only establishes that the product has downlink intent.

Contact and downlink assumptions are introduced in the next step.

## Example: radiation histogram

The `radiation_histogram` product connects several earlier tutorial concepts:

```text
payload lifecycle
-> histogram generated
-> data product exists
-> science storage intent
-> high priority downlink intent
```

It is produced by:

```text
radiation_event_payload
```

and represents the main science output of the current Reference Mission.

This is the bridge between payload activity and mission data handling.

## Example: scenario evidence log

The `scenario_evidence_log` product exists because OrbitFabric is evidence-oriented.

The tutorial is not only interested in science products. It also needs operational evidence that explains what happened in a scenario.

That is why the model includes an engineering evidence product with deferred downlink policy.

## What is deliberately not modeled yet

This data-product contract does not define:

- file formats;
- binary serialization;
- compression algorithms;
- filesystem layout;
- database schemas;
- actual queue implementation;
- RF transfer protocol;
- complete downlink scheduling.

Those are implementation or later integration concerns.

At this stage, the Reference Mission only defines contract-level product intent.

## Link to later model areas

Later tutorial steps will use data products to explain:

- contact and downlink assumptions;
- nominal science downlink;
- delayed downlink and backlog behavior;
- generated documentation surfaces;
- scenario evidence;
- future Studio navigation from payload activity to product status.

Data products are the bridge between mission behavior and durable mission outputs.

## Modeling rule introduced in this step

The tenth rule is:

```text
Model data products as mission outputs with storage and downlink intent.
```

Do not model data products as arbitrary files.

Add a data product when the mission needs to preserve science, housekeeping or evidence in a way that can be validated, documented and reasoned about.
